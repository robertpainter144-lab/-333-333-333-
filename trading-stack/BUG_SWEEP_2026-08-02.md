### `ibkr_bot/watcher.py:309` — watch_once clobbers stop_state.json with a stale in-memory copy, undoing profit-step/cancel/modify writes  ✅ CONFIRMED

## Cross-cutting: money/risk directive enforcement — 3 confirmed high, 3 med/low

### `ibkr_bot/main.py:150` — Order path enforces only a per-order $50 cap, never the aggregate $20 IBKR approval gate  ✅ CONFIRMED

place_share_buy() computes notional = qty * ref_price for the SINGLE new order and only refuses when notional > MAX_ORDER_USD (=$50). It never sums existing positions/pending orders, never computes projected total exposure, and never calls notify.needs_approval()/notify.propose_trade(). The standing rule is an AGGREGATE $20 ceiling requiring an ntfy push approval BEFORE firing; this code path (the only bot buy path that adds equity exposure) has no aggregate accounting at all. Even the follow-on notify_order_placed() reports total_exposure_after = qty*limit, i.e. just this order, so the notification also misstates aggregate exposure.

**Failure scenario:** Account already holds ~$18 of positions (e.g. leftover F/AAL/PINS from the three-arm experiment). Operator or launchd runs `python3 main.py --symbol F --qty 1` (~$11). notional $11 < $50 so it fires immediately; aggregate becomes ~$29, over the $20 ceiling, with no approval request and no ntfy prompt. Larger --qty values scale this arbitrarily up to the $50 per-order cap per invocation, and repeated invocations stack with no ceiling.

### `scanner/sources/prop_desk.py:82` — Prop-desk can place LIVE orders pre-promotion; promotion gate is advisory-only  ✅ CONFIRMED

Rule: prop-desk stays signal-only until promoted. But _submit_order() only skips when ALPACA_MODE=='signal_only' or the key is missing; the default mode is 'paper' and any BUY/SELL signal executes. ## qc_portfolio (live on VM) — 3 confirmed high, 7 med/low

### `qc_portfolio/portfolio_engine.py:246` — compute_target ignores exposure_level — daily rebalance undoes the DD ladder  ✅ CONFIRMED

check_stop_losses reduces _state['exposure_level'] when a drawdown-ladder tier fires (e.g. -15% -> 50% invested) and keeps the tier in cooldown for DD_LADDER_COOLDOWN_DAYS. But compute_target() builds targets as total_equity * weights with no exposure_level scaling anywhere (grep confirms exposure_level is only read/written inside check_stop_losses and backtests). The live rebalance path (main.py do_rebalance, runs daily at 9:31) therefore re-buys straight back to 100% invested the very next morning. Worse, the fired tier stays in tiers_fired, so after the buyback the same tier cannot fire again until a new peak or the 21-day cooldown — the re-bought book rides further drawdown unprotected until the next deeper tier.

**Failure scenario:** Portfolio falls 15% from peak intraday Monday; ladder sells down to 50% invested. Tuesday 9:31 the scheduler runs do_rebalance -> compute_target(equity) targets 100% deployment -> rebalance_orders buys everything back. The de-risking lasted less than one session, and if the market drops another 4% the 15% tier is still in tiers_fired so no ladder sell occurs until the 20% tier.

### `qc_portfolio/market_data.py:83` — Swallowed /positions API error returns [] — rebalance treats it as a flat book and re-buys the whole portfolio  ✅ CONFIRMED

_get() catches every exception (timeout, 500, auth blip) and returns [] for /positions, printing only. Callers cannot distinguish 'no positions' from 'API failed'. In do_rebalance (main.py line 79), positions = md.get_positions() right before rebalance_orders: an empty list makes current_dollars empty, so diff = full target for every symbol and the engine emits buy orders for the entire ~$53k book it already holds. validate_equity does NOT protect here: with positions=[] the local estimate deviates, equity is rejected, and the function returns last_good (still ~$53k > 0), so the rebalance proceeds. **Failure scenario:** Alpaca sandbox returns a transient 502 on GET /positions at 9:31 while /account and POST /orders work. get_positions() -> []. rebalance_orders computes buy orders for all currently-held symbols at full target size; whatever free cash exists is spent buying duplicate shares, unbalancing the book with no error surfaced anywhere but a print.

### `qc_portfolio/portfolio_engine.py:509` — Profit ratchet baseline is unrealized P&L — any sell during the day spuriously breaches the floor and dumps 50% of the book  ✅ CONFIRMED

check_profit_ratchet computes current_pl as the sum of unrealized P&L ((price - avg_entry) * qty) and anchors session_open_pl/ratchet_floor to that quantity. When a position is sold intraday (trail/hard/time stop, profit_step half-sell, or rebalance trim), its unrealized gain leaves the sum even though no money was lost — the gain was realized. current_pl instantly drops below the floor and the ratchet sells PROFIT_RATCHET_SELL_FRAC (50%) of every remaining position. profit_step is a guaranteed trigger: it fires exactly when a position is up ~2 ATR (large unrealized gain) and sells half of it.

**Failure scenario:** Session gain hits +$80, ratchet arms with floor ~+$48. At 11:00 a winner with $45 unrealized gain hits its profit_step and half is sold; unrealized P&L drops ~$22 with zero actual loss. Next 30-min check: current_pl < floor -> '[RATCHET] Floor breached' -> 50% of every position liquidated on a day the account is actually at its high.
